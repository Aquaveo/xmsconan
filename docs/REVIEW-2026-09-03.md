## Part A — Package review

### Health snapshot

No `shell=True`, no module-level mutable globals, one TODO, consistent
`subprocess.run([...])` everywhere. The recent refactors (`build_toml`
API, `constants.py`, `ci_options.py`) show the direction is good. What
follows is structural debt and process gaps, not breakage.

Coverage low spots: `ci_tools/wheel_deploy.py` 62 %,
`generator_tools/profile_generator.py` 67 %, `build_tools/build_library.py`
77 %. `pyyaml` reaches the CI test job only because conan pins
`PyYAML<7,>=6` — nothing declares it.

### Highest leverage

**R1. `XmsConanPackager` does everything.** `package_tools/packager.py:530`,
2121 lines, the highest-churn file in the repository (28 of the last 100
commits). One class owns matrix generation (`:913`), filtering (`:1188`),
running conan (`:1231`), sharded tests (`:1392`), upload (`:1452`), wheel
extraction (`:1499`), dependency-lib collection (`:1621`), Linux wheel
repair (`:1669`), profile serialization (`:1711`), CMake presets (`:1930`)
and table printing (`:2038`). Temp-dir cleanup is in `__del__` (`:673`),
which is non-deterministic and skipped when `__init__` raises. → plan 6.1.

**R2. The copied recipe is hand-synced.** `xms_conan2_file.py` cannot
import from the package (`constants.py:7-11`), so `SUPPORTED_PYTHON_VERSIONS`,
`TESTING_FRAMEWORKS`, `PYTHON_BINDING_TYPES`, `GENERATOR_FOLDER_SUFFIXES`
and the msvc-192 literal are duplicated and held together by four pinning
tests. → plan 6.2.

**R3. Four credential resolvers.** `ci_tools/credentials.py` (file only),
`build_tools/vs2019_build.py:321` (file → `CONAN_*` env → toml →
`"aquaveo"`), `ci_tools/conan_setup.py:121` (`--password-file` →
`$CONAN_PASSWORD`), `ci_tools/wheel_deploy.py` (CLI → `AQUAPI_*` env →
toml). Different precedence, different env-var families, two `Credentials`
shapes. → plan 6.3.

**R4. `vs2019_build.py` (1551 lines) carries workspace data.** The
`LIBRARIES` catalogue (`:198`) duplicates the dependency order in the
workspace `CLAUDE.md`; `os.environ["XMS_VERSION"] = version` (`:1051`)
mutates the process environment; `CONAN_PIN = "~=2.31.0"` (`:130`)
disagrees with `pyproject.toml`'s `conan>=2`. → plan 6.4.

### CI and packaging of xmsconan itself

**R5. Python matrix is 3.13 only** (`.github/workflows/xmsconan-ci.yaml`)
while `requires-python >= 3.10` and the classifiers claim 3.10 / 3.14.
The `toml` fallback branch in `build_toml.py:14-17` (< 3.11) never runs in
CI. → plan 1.2.

**R6. No coverage gate on the coverage tool.** The low modules are in the
snapshot above. → plan 1.3.

**R7. Dev tooling is undeclared.** flake8 and its four plugins exist only in
the workflow YAML; CI does `pip install pytest` rather than `.[test]`, so
`pyyaml` arrives by accident via conan. No pre-commit, tox or Makefile.
→ plan 1.1.

**R8. `toml` is still a dependency** (unmaintained, not TOML 1.0).
`ci_tools/credentials.py:56` calls `toml.load` unconditionally while
`build_toml.py` prefers `tomllib` — two parsers for two files. → plan 1.4.

**R9. Reproducibility.** `uv.lock` is gitignored, no dependency has an
upper bound, Actions are pinned inconsistently (`checkout@v4` by tag,
`get-git-tag` by SHA — and that action is replaceable by
`${{ github.ref_name }}`), no Dependabot. → plan 7.1.

**R10. The `integration` pytest marker never runs in CI.** → plan 7.2.

### Code-level consistency

**R11. Five copies of `_configure_logging`** —
`generator_tools/ci_file_generator.py:84`,

**R13. `print` versus `logging`.** `vs2019_build` has 24 prints,

**R14. Type hints are patchy.** `packager.py` 6 of 52 defs annotated,

## Part B — Credential handling in the generated CI

### Short answer

Mostly sound — the code side is careful, and the one leak that existed
(#125, `33a9d24`) is fixed at the source. But there are two real gaps in the
*CI configuration* around it, one deliberate exception that the repository's
own threat model contradicts, and a guard test that would not catch the
next variant of the #125 bug.

### What is protected correctly

- **Conan logins never see the password on argv.**
  `ci_tools/conan_setup.py:23-50` builds `CONAN_PASSWORD_<REMOTE>` in the
  child environment and runs a bare `conan remote login <remote>`
  (`:113-118`); `test_main_has_no_password_flag` pins that there is no
  `--password` flag. `xmsconan vs2019 setup` resolves via `--password-file`
  / env / `~/.xmsconan.toml` the same way.
- **Profiles are credential-free.** `generate_configurations` no longer puts
  `AQUAPI_*` into `[buildenv]`, so conan's "Input profiles" echo is clean;
  `test_generate_configurations_keeps_credentials_out_of_buildenv`
  (`tests/test_packager.py:2000`) pins it.
- **Docker forwards by name.** `ci_tools/docker_run.py:52-82` emits
  `-e AQUAPI_PASSWORD` (no value) and mounts `~/.xmsconan.toml` read-only.
- **GitHub secrets flow through `env:` from `${{ secrets.* }}`**
  (`github-ci.yaml.jinja:119-125`), so GitHub masks them in logs; every
  deploy step is gated on `refs/tags/`; forks never receive secrets.
- **Nothing echoes an environment.** No `shell=True`, no `set -x`, no logger
  prints an env dict. The command-echo loggers
  (`coverage_tools/coverage_generator.py:172`,
  `build_tools/build_library.py:282/389/402`) only print `build.py` / gcovr /
  conan argv, which carry no credentials. `_serialize_profile` logs dropped
  key *names* only. Every pip index URL is the literal anonymous
  `public.aquapi…` host — no `user:pass@` anywhere.

### Gaps, most important first

**S1. GitLab masks nothing unless told to, and the docs never say so.**
GitHub masks `secrets.*` automatically; GitLab masks a CI/CD variable only
when it is flagged **Masked**, and hands it to *every* pipeline unless it is
flagged **Protected**. USAGE §10.2 (`docs/USAGE.md:622,630`) lists the four
required variables, but neither README, USAGE nor the template header
mentions either flag (zero grep hits), and only the `only: tags` deploy
jobs need the values. → plan 0.1 (settings), 2a.4 (docs).

**S2. `xmsconan_wheel_deploy` passes the devpi password on a command
line** — `ci_tools/wheel_deploy.py:60-62`:
`["devpi", "login", username, "--password", password]`. USAGE §13
(`:818-825`) documents it as the one exception because devpi-client offers
no env var, and that is true (devpi-client 7.3.0 `login.py:11-16`: argv or
an interactive `getpass` hook). But the package's own docstrings
(`conan_setup._login_environment`, `docker_run._build_env_flags`) explain
why argv is unacceptable — Event 4688 / Sysmon / `ps` capture — and this
runs in the generated GitHub jobs on all three platforms, in the GitLab
deploy jobs, and inline in xmsconan's own `.github/workflows/xmsconan-ci.yaml`.
The exception is now avoidable: `uv publish` reads `UV_PUBLISH_USERNAME` /
`UV_PUBLISH_PASSWORD` / `UV_PUBLISH_URL` from the environment (verified in
the installed uv), speaks devpi's PyPI-compatible upload endpoint, and uv
is already the toolchain in every generated job. → plan 2a.1, 2b.2.

**S3. GitHub secrets are scoped to the whole job, not the steps that need
them.** `CONAN_PASSWORD` and `AQUAPI_PASSWORD` sit in job-level `env:`
(`github-ci.yaml.jinja:119-125` and its three repeats;
`github-coverage.yaml.jinja:34-39`). Every step inherits them — including
`conan create`, which builds a venv, `pip install`s numpy / pytest /
pytest-cov from PyPI (`xms_conan2_file.py:971-979`) and runs the library's
own test suite. Log masking only protects against *printing*; a compromised
dependency or test reading `os.environ` and posting it elsewhere is not
masked. Only two steps consume the values. → plan 2b.1; design §3.4.

**S4. The #125 guard is a deny-list, and the ephemeral profile is still
printed in full.** `test_generate_configurations_keeps_credentials_out_of_buildenv`
only checks `key.startswith("AQUAPI_")` (`tests/test_packager.py:2011`),
while `create_build_profile` → `printer.print_profile`
(`packager.py:1769-1775`, `printer.py:44`) writes the whole profile to
stdout on every configuration. A future `CONAN_PASSWORD_*` or
`GITHUB_TOKEN` added to `buildenv` would pass the test and land in the
log. → plan 2a.2.

**S5. A docstring still asserts the pre-#125 reasoning.**
`_serialize_profile`'s `public_only` doc (`packager.py:1718-1721`) says the
temporary profile "keeps the full environment because the build needs it
and the file is discarded with its temporary directory" — the exact argument
#125's commit message called backwards. → plan 2a.3.

**S6. Minor.** `AQUAPI_URL` is stored as a GitHub *secret*
(`secrets.AQUAPI_URL_DEV`) while the same URL is hard-coded in the GitLab
template and in xmsconan's own workflow. Masking a public URL hides
`Looking in indexes: ***` diagnostics without protecting anything.
→ plan 2b.1.
